# 第一讲｜AI 辅助科研导论与八阶段研究链路

## 导读

生成式人工智能正在降低许多科研动作的成本：研究者可以更快地扩展关键词、理解陌生概念、定位代码错误、生成实验脚本、整理结果或修改文字。成本降低并不意味着研究质量自动提高。相反，当生成、修改和实验的速度显著增加时，未经核验的引用、含有数据泄漏的代码、不公平的对照、丢失的失败记录和缺乏边界的结论也可能更快地扩散。

因此，本课程不把“会不会使用某个 AI 工具”作为核心问题，而提出一个更严格的问题：

> 当 AI 参与科研之后，我们如何保证问题仍由研究者定义，证据仍可核验，实验仍可复现，结论仍有边界，责任仍由人承担？

本讲介绍贯穿全课的八阶段研究链路，并用一次最小的 OpenCode 交互说明 Agent 如何进入科研工作流。你不需要在第一讲掌握复杂的 Agent 架构，但需要从一开始养成三个习惯：

1. 把 AI 的任务和权限说清楚；
2. 把 AI 的输出视为需要核验的候选，而不是事实；
3. 把关键输入、人工决定、文件变化和核验结果留下记录。

### 适用对象与先修要求

本课程面向 CS / AI 及相关方向硕士生、博士生。先修要求：Python｜机器学习基础｜Git｜命令行｜英文论文阅读。课程会提供研究模板和课堂案例，但不会从 Python、Git 或终端基础开始教学；英文文献保留原文，教师提供中文阅读范围、术语和问题。

## 学习目标

完成本讲后，你应该能够：

1. 说明 AI 辅助科研与“自动生成一份报告”的差别；
2. 用八阶段研究链路定位当前动作、工件和回退位置；
3. 解释四个研究门为什么能够减少错误累积；
4. 区分线索、证据、研究判断和结论；
5. 在 OpenCode 项目中完成一次范围受限、经过人工确认且留下记录的交互；
6. 为自己的研究兴趣写出初步问题和八阶段链路草图。

## 一、AI 能提高效率，但不能承担研究责任

### 1. AI 可以参与哪些科研动作

AI 可以在几乎所有科研阶段提供辅助，例如：

| 科研动作 | AI 可能提供的帮助 | 主要风险 |
| --- | --- | --- |
| 文献检索 | 扩展关键词、生成检索式、初筛材料 | 虚构文献、遗漏反方证据、来源不可追溯 |
| 论文阅读 | 解释术语、提取方法与结果、比较论文 | 错读限定条件、混淆作者主张与模型推断 |
| 问题形成 | 生成候选问题、反例和可证伪命题 | 追求新颖表述而忽略真实价值与可行性 |
| 代码与调试 | 生成脚本、定位错误、补测试 | 引入数据泄漏、修改无关代码、绕过失败 |
| 实验迭代 | 生成配置、调度实验、汇总结果 | 修改评价协议、超出预算、只保留成功结果 |
| 结果分析 | 生成表格、分类失败、发现异常 | 把相关性写成因果、忽略不利结果 |
| 论文写作 | 组织结构、润色表达、检查一致性 | 证据链断裂、引用不实、贡献与署名混乱 |
| 审稿模拟 | 从 rubric 出发发现问题 | 将模型意见误当作真实同行共识 |

这些动作有一个共同点：AI 可以生成候选、执行重复步骤或帮助发现问题，但它无法自动获得对研究背景、学科规范、数据来源和潜在后果的完整责任。

2026 年 Nature 论文 *Towards end-to-end automation of AI research* 报告：The AI Scientist 能从构思一路走到实验、成文和自动评审；研究团队从其输出中人工筛选 3 篇送入 ICLR workshop 评审，其中 1 篇平均得分 6.33，超过该 workshop 的平均接受阈值。但另外 2 篇没有达到接受线，研究团队内部复核认为 3 篇都未达到 ICLR 主会标准。三篇投稿均在评审后按预先约定的协议撤回；这里讨论评审分数与团队复核，不将其写成正式发表结果。这一案例展示了端到端研究自动化的能力与质量差距：**完整产物已经出现，稳定的高水平研究质量仍未成立。**

### 2. 把 AI 建议拆成待检验主张

阅读卡是按字段记录论文问题、方法、结果、局限和原文位置的材料。设想你正在写一项阅读方法研究的结论，AI 建议：“结构化阅读卡可以减少摘要遗漏，因此适合所有论文阅读任务。”这句话是课堂构造，尚无相关原文或实验记录。

先圈出需要检查的词。“减少”提出效果比较，需要说明与谁比、遗漏怎样计算、结果在哪里；“所有”扩大适用范围，需要检查哪些论文与任务被覆盖。AI 建议可以帮助提出问题，支持效果和范围的依据必须来自相应材料与核验。

| 检查对象 | 要回答的问题 | 记录方式 |
| --- | --- | --- |
| 来源核验 | 拟用转述是否对得上原文？ | pending / verified / verified-with-caveat / rejected |
| 证据作用 | 这项材料支持、限制或反驳哪条主张？ | 先写主张，再注明材料作用 |
| 结论方向 | 当前观察让我们支持、反驳还是仍不能判断？ | 绑定具体命题、依据和范围 |
| 工件成熟度 | 这份项目材料经过什么检查？ | draft / review / approved / stable |

这四个维度分别记录。文字草稿可以包含待检验主张；核验过的来源仍有适用边界。`stable` 是课程的成熟度约定，有限结果、负结果和未决项都可按实际依据进入论文式报告。

把规模放大到 AI 生成的整篇论文，同样先检查效果、比较条件和适用范围，再判断研究质量。

### 3. 2026 年的新问题：效率之后如何治理

2026 年 Nature 围绕 AI for Research 的讨论已经不只问“AI 能否完成更多科研步骤”，还追问三个系统问题：机构、资助方与出版方如何建立透明和护栏；问题框定、实验设计、指导与责任为何仍需要人类；速度与发表激励是否会让研究方向趋同。Hao 等人对跨学科论文数据的观察性研究也提示：个体产出或影响扩大，不自动等于科学共同体探索范围扩大。

这些材料在本课承担不同证据角色：AI Scientist 论文展示系统能力；Hao 等人的论文提供观察性实证结果；Nature 评论与社论提出治理和研究生态问题。评论不是实验结果，观察性关联也不能自动写成因果结论。

### 4. 哪些判断不能外包

在本课程中，执行支持可以交给 Agent——检索、起草、整理 diff 都可以在 OpenCode 里完成；但以下判断必须由学生亲自作出并能解释理由，且每次 AI 参与都要留下可审计记录：

- 这个问题是否值得研究；
- 问题的范围和非例是什么；
- 某项材料是否真的支持相应主张；
- 候选假设是否符合基本约束并且可以被推翻；
- baseline、数据、指标和对照是否公平；
- 结果是否足以支撑结论；
- 工作流是否越权、泄露数据或改变评价标准；
- 失败是否被完整记录；
- AI 的参与是否得到如实披露。

“模型建议这样做”“Agent 自动完成了”都不能作为研究判断的充分理由。研究责任不会因为执行者从脚本变成 Agent 而消失。

### 5. 一个重要区分：报告是产物，研究是过程

现代 AI 系统可以围绕一个主题搜索材料并生成结构完整、带有引用的报告。这类系统对信息搜集和初步理解很有价值，但报告的完整外观不能证明研究过程成立。

假设我们输入题目“长上下文模型是否真正改善了复杂推理”。系统可能生成定义、方法分类、代表论文和总结。然而，一个研究项目还必须回答：

- “长上下文”“复杂推理”和“改善”分别如何定义？
- 输入长度增加与推理能力提高是否被混淆？
- 比较的模型是否拥有相同计算预算和工具条件？
- 是否存在支持相反结论的实验？
- 哪个观察结果能够推翻当前解释？
- 结论适用于哪些任务，不适用于哪些任务？

如果这些问题没有被明确处理，即使报告文字流畅，也只能算信息产物，不能算完成了一个科研闭环。

## 二、八阶段研究链路

本课程使用以下八阶段组织研究：

> 问题定义 → 第一性原理分析 → 机制假设 → 外部输入摄取 → 证据整理 → 研究判断 → 原型验证 → 回写与表达

它不是只能单向前进的流水线。阅读文献可能迫使你重新定义问题，失败实验可能推翻机制假设，写作时发现证据断裂也可能要求补做实验。八阶段的价值在于：无论发生回退还是迭代，你都知道当前在修改什么、为什么修改、需要留下什么工件。

> **本课学习边界**：课堂只用一条研究主张练习“现在位于哪一阶段、为何回退、留下什么工件”。下面八个分节是后续课次的导航与查阅材料，不要求在第一课背诵术语、填满所有字段或完成各阶段工件。

四条典型回退：

- 阅读发现定义错误 → 回到问题；
- 实验推翻机制 → 回到假设；
- 写作暴露证据断裂 → 回到取证；
- Agent 越权 → 回到任务与权限。

## 2.1 阶段一：问题定义

问题定义不是选择一个热门主题，而是明确要解释或改善的结构性问题。

一个宽泛主题：

> 大模型在科研中的应用。

一个较具体的问题：

> 在来源受限且需要逐条引用核验的文献综述任务中，加入证据追踪表是否能够降低 AI 生成摘要中的主张—来源错配率？

后者至少给出了：

- 条件：来源受限、逐条核验；
- 对象：AI 生成的文献综述摘要；
- 干预：加入证据追踪表；
- 结果：主张—来源错配率；
- 可比较性：可以与不使用追踪表的流程比较。

问题定义阶段应写出：

1. 研究对象与场景；
2. 明确包含的范围；
3. 明确不包含的非例；
4. 至少一个可证伪命题；
5. 在课程周期内完成最小验证的可能性。

非例尤其重要。它说明“什么不算本问题”，防止项目随着检索不断膨胀。例如，上述问题的非例可以是：

> 本项目不比较不同大模型的通用写作质量，也不评价综述是否具有语言美感。

可证伪命题则说明什么观察会使当前主张不成立：

> 如果加入证据追踪表后，错配率没有下降，或者人工核验成本显著增加且无法接受，则“追踪表改善该科研动作”的主张不成立。

## 2.2 阶段二：第一性原理分析

第一性原理分析要求暂时放下具体工具名称，从问题成立所依赖的基本条件开始推导。

继续使用证据追踪表的例子。要降低主张—来源错配率，至少需要：

1. 每条关键主张能够指向具体来源位置；
2. 来源中确实存在支持该主张的内容；
3. 核验者能够区分原文主张、合理推断和模型新增内容；
4. 对照流程与工作流使用相同材料和相同评价标准。

这些条件比“使用某个模型”“安装某个 Skill”更稳定。工具可以替换，但如果来源无法定位，或评价标准在实验过程中变化，结论仍然不成立。

第一性原理阶段常用的问题包括：

- 如果主张成立，哪些条件必须满足？
- 哪些约束来自任务本身，而不是当前工具？
- 哪些变量必须保持一致，比较才公平？
- 哪个最简单的反例足以推翻当前解释？

输出通常是一份必要条件、关键约束和可检验前提清单。

## 2.3 阶段三：机制假设

机制假设回答“为什么预期结果会发生”，而不只是“预期结果是什么”。

结果预测：

> 使用证据追踪表会降低错配率。

机制假设：

> 证据追踪表要求每条主张在生成时绑定来源位置，使无来源主张更容易被发现，并降低后续写作阶段把模型推断误写成原文结论的概率。

一个好的机制假设应该：

- 与问题和第一性原理约束一致；
- 指出中间过程，而不只预测最终指标；
- 对应可观察现象；
- 允许被实验支持、削弱或推翻；
- 能与其他解释区分。

AI 可以帮助生成候选机制，但候选越多不代表研究越好。你需要记录保留或放弃某个假设的理由。

## 2.4 阶段四：外部输入摄取

外部输入不仅是论文，还可以包括：

- 官方文档和标准；
- 上游代码仓库与版本记录；
- 数据集说明和许可；
- 实验日志；
- 领域专家反馈；
- 可靠的工程实践记录；
- 用于探索的博客、issue 或社交媒体线索。

不同来源承担不同角色。论文可以提供理论或实验依据，代码可以验证实现细节，issue 可以暴露失败模式，博客可能帮助发现关键词。来源类型本身不自动决定可信度，但关键结论必须尽可能回到可核验的一手材料。

外部输入摄取阶段至少记录：

- 来源是什么；
- 为什么纳入；
- 它可能支持或反驳什么；
- 是否已经核验；
- 有哪些许可、隐私或时效性风险。

AI 生成的搜索结果或摘要只能作为定位来源的线索，不能单独成为证据。

## 2.5 阶段五：证据整理

文献数量多不等于证据充分。证据整理要把材料与假设、主张和缺口连接起来。

一个简化的证据地图：

| 证据项 | 可核验来源 | 支持什么 | 不能支持什么 | 状态 |
| --- | --- | --- | --- | --- |
| E1：人工标注的错配样例 | 样例 ID 与原文位置 | 当前流程存在错配 | 不能说明追踪表能够改善 | verified |
| E2：追踪表流程运行记录 | 运行日志与输出文件 | 工作流能够建立主张—来源连接 | 不能单独说明连接准确 | verified |
| E3：对照评价结果 | 固定 rubric 下的前后对比 | 追踪表是否降低错配率 | 样本小，外部有效性有限 | review |

本课程采用以下证据要求：

- 普通事实陈述应注明来源；
- 关键结论至少绑定一项可核验的直接证据或实验结果，并连接到上游研究判断；
- 标记为 `stable` 的结论原则上需要两项相互独立的证据；
- 不强制证据必须来自某个固定类型组合；
- 只有单一证据时，记录支持强度、适用边界、缺失证据和待验证状态；
- 冲突证据必须呈现，不能只保留支持当前观点的部分。

“独立”并不简单等于两个不同网页。两篇互相转载的文章并不是两项独立证据；同一代码路径运行两次也未必构成独立验证。独立性应来自来源、测量、重复实验、对照、消融或分析路径之间的实质差异。

## 2.6 阶段六：研究判断

研究判断是从证据到行动的有理由取舍。它不同于事实，也不同于假设。

例子：

> J1：主要评价指标采用“主张—来源错配率”，不使用通用语言质量评分。理由是本项目研究可追溯性而不是语言流畅度；适用边界是带引用的文献综述任务；仍待验证人工标注一致性。

一条完整研究判断至少包含：

- 判断内容；
- 取舍理由；
- 适用边界；
- 所依据的证据或机制假设；
- 是否仍待验证；
- 判断改变后会影响哪些工件。

研究判断记录能够防止一种常见现象：实验完成后，研究者根据结果反向改写“最初为什么这样设计”。保留当时的理由，才能诚实分析哪些判断正确、哪些判断需要修正。

## 2.7 阶段七：原型验证

原型验证不要求一开始完成大规模系统。课程强调“能够改变研究判断的最小验证”。

实验规格应回答：

- 验证哪个假设？
- 自变量、因变量和控制变量是什么？
- baseline 是什么？
- 输入数据或样本如何选择？
- 使用什么指标或 rubric？
- 预算、运行次数和停止条件是什么？
- 什么结果支持、削弱或推翻假设？
- 失败后如何恢复或回退？

如果使用 Agent 或自动化循环，还需要明确：

- 允许访问哪些文件、数据和网络资源；
- 允许写入和执行什么；
- 哪些动作必须人工确认；
- 是否允许修改评价代码；
- 失败日志是否保留；
- 工作流何时停止。

原型验证的输出不仅是最终指标，还包括配置、环境、日志、失败、异常和人工审核记录。

## 2.8 阶段八：回写与表达

研究表达不是最后才开始的包装工作。结果出现后，必须回写到假设、证据地图和研究判断。

一个基本论证单元包含：

> 主张 → 证据 → 推理 → 边界

例如：

> 在本课程使用的 20 个带引用摘要样例中，证据追踪表降低了人工标注的主张—来源错配率（证据：E3）。这一结果与“生成时绑定来源位置能够暴露无来源主张”的机制假设一致，但样本规模较小，且只覆盖计算机领域论文，因此不能推断到所有学科或长篇综述。

这段表达没有只写“方法有效”，而是同时写出了场景、证据、机制关系和适用边界。

如果实验没有支持原假设，回写同样重要：

> 当前结果未显示追踪表降低错配率。运行记录表明主要错误来自对原文限定条件的误读，而不是来源缺失，因此原机制假设需要修改。

负结果并不等于项目失败。隐藏负结果、改变评价口径或事后夸大解释才会破坏研究可信度。

## 三、四个研究门

四个研究门把八阶段链路转化为课程中的质量检查点。

| 研究门 | 时间 | 核心问题 | 主要工件 |
| --- | --- | --- | --- |
| 问题门 | 第 6 课 | 问题值得问、问得清、做得完吗？ | 问题定义、阅读卡、证据地图、非例、可证伪命题、第一性原理 |
| 判断门 | 第 9 课 | 方案有依据，实验能够改变判断吗？ | 机制假设、研究判断、baseline、实验规格、复现说明 |
| 验证门 | 第 13 课 | 结果和工作流真的经过评价吗？ | 原型、实验记录、个人 Agent Workflow、评价、失败与人工审核 |
| 论证门 | 第 16 课 | 最终主张能追溯到证据和决定吗？ | 报告、证据链、工作流、伦理披露、AI 使用记录、复盘 |

研究门不是额外制作四套文档。你始终维护同一个项目，门检查的是当前项目版本是否满足进入下一阶段的条件。

未通过某个研究门时，应回到对应环节修复根因。例如：

- 缺少直接证据：回到外部输入和证据整理；
- 问题过大：回到问题定义；
- baseline 不公平：回到研究判断和实验规格；
- 工作流只能运行但无法评价：回到任务契约与 Evals；
- 结论无法追溯：回到实验记录、证据地图和回写。

**评分依据与细则公开**：课程评分比例为文献与问题定位 25%、实验设计与可复现性 30%、原型与 Agent Workflow 实践 25%、表达、伦理与复盘 20%；每个维度均公开“卓越／达标／待改／不达标”四级可观察锚点，详细条目见 [考核方案](../../course/assessment.md)。评分以四个研究门的实际工件为证据，不以课堂印象、AI 使用量或平台选择评分。细则提高判断透明度，但不能保证任何论文发表。

## 四、执行环境服务于研究任务

### 1. OpenCode 在课程中的角色

OpenCode 是课程的主要课堂执行环境，用来承载项目文件、模型交互、工具调用、命令执行和运行记录。Claude Code、Codex 或其他合规且功能等价的环境可以完成同类任务；DeepSeek、Qwen 等是可以由这些环境连接的模型后端，不与执行环境处于同一层。

课程始终按三层区分：

1. **研究任务与边界**：问题、输入、输出、成功标准、权限和人工确认；
2. **执行环境／harness**：把声明的边界落实到文件、工具、网络、确认和 trace；
3. **模型后端**：在已声明 Context 与权限内生成候选或执行受限动作。

使用统一平台的目的不是要求每位学生记住相同命令，而是让以下工作流要素能够被观察：

- 任务是如何表达的；
- Agent 获得了哪些 Context；
- 它可以使用哪些工具；
- 它读写了哪些文件；
- 人在哪个位置审核；
- 输出如何写回研究工件；
- 失败如何记录和恢复。

学生可以在合规前提下使用功能等价环境，但不能因为使用某个平台、模型或现成 Skill 获得额外分数。

### 2. Agent Workflow 的八个组成部分

后续课程会反复使用以下分析框架：

| 组成部分 | 需要回答的问题 |
| --- | --- |
| 任务契约 | 输入、输出、成功标准和不适用范围是什么？ |
| Context | Agent 能看到哪些论文、代码、数据和项目工件？ |
| Memory / 状态 | 哪些信息跨步骤保留，保存在哪里？ |
| 工具与权限 | 能读取、写入、执行和联网到什么范围？ |
| 执行循环 | 如何计划、行动、观察、评价和停止？ |
| 工件与追踪 | 输入、日志、输出和上游决定如何关联？ |
| Evals 与人工审核 | 与什么对照，谁在什么位置确认？ |
| 失败恢复 | 超时、无效输出、工具失败或越权时怎么办？ |

现成 Agent 或 Skill 只是这些设计要素的一种封装。课程不会把安装和调用步骤当作学习目标，而会要求你拆解这些逻辑，并针对自己的科研动作重新设计。

### 3. 最小权限原则

第一讲的项目默认只允许 Agent 访问课程项目所需内容。不要为了“方便”开放整个个人目录、云盘、未公开数据和凭据文件。

权限设计可以分为：

- 只读：`AGENTS.md`、公开论文、当前问题初稿；
- 可写：项目内指定 Markdown 或代码文件；
- 可执行：明确列出的安全检查、测试或脚本；
- 需确认：联网、安装依赖、大范围修改、外部写入；
- 禁止：敏感数据、凭据、无关目录、删除失败记录、修改评价协议。

权限不是一次设置后永久不变。随着项目进入实验阶段，可以在记录理由和风险后逐步开放必要权限。

## 五、一次最小可审计科研交互

下面的练习服务于一个简单目标：收敛初步研究问题。它故意分成两轮。

### 第一步：只允许分析，不允许写入

任务契约示例（可直接粘贴进 OpenCode 使用；它读取你项目里的文件，无需改写）：

```text
读取 AGENTS.md 和 problem-definition.md 中的当前问题。

目标：
提出三个范围收敛建议。

每条建议必须包含：
1. 建议修改的范围；
2. 依据；
3. 可能损失；
4. 需要研究者确认的问题。

限制：
- 不修改任何文件；
- 不访问项目以外目录；
- 不联网；
- 不把建议写成已证实事实。
```

这种写法把“帮我改一下题目”转换为可审查任务。第一轮禁止写入，是因为学生还没有决定采用哪条建议。

### 第二步：人工决定后受限写回

研究者选择建议后，再授权写入：

```text
根据我确认的第【N】条建议：

1. 只修改 problem-definition.md 的“当前问题”段；
2. 将原表述保留到“修改记录”（starter-template §3 修改记录子节）；
3. 在 ai-usage-log.md 增加本次交互摘要；
4. 不修改其他文件，不访问网络。

完成后给出：
- 修改摘要；
- 实际修改的文件；
- 仍需人工核验的内容。
```

把【N】换成你实际选择的那条；对每条建议的采纳／拒绝及理由，写入 `notes/` 或 AI 使用记录，作为同伴互查"复原建议—判断—修改"的依托。

### 第三步：人工核验

至少检查：

- diff 是否只包含授权范围；
- 问题含义是否被模型悄悄改变；
- 新增内容是否被误写为事实；
- 原始表述是否保留；
- AI 使用记录是否包含用途、Context、输出用途和核验方式。

### 第四步：记录失败

如果 Agent 修改了无关段落、引入不存在的事实或要求访问其他目录，不要静默重跑直到成功。应记录：

- 失败表现；
- 可能原因；
- 是否涉及权限或任务契约缺陷；
- 如何修改工作流；
- 修改后结果。

失败记录是后续评价工作流的重要证据。

## 六、贯穿案例：从主题到最小研究闭环

下面用一个虚构课程项目展示八阶段之间的连接。

### 初始主题

> AI 辅助论文阅读。

### 问题定义

> 对需要逐条核验引用的计算机论文阅读任务，结构化阅读卡是否能够降低 AI 摘要中的限定条件遗漏率？

非例：

- 不比较不同模型的通用问答能力；
- 不评价写作风格；
- 不处理需要专业实验设备的学科。

可证伪命题：

> 如果结构化阅读卡与普通摘要相比没有降低限定条件遗漏率，则当前主张不成立。

### 第一性原理

- 限定条件必须能够从原文定位；
- 两种流程使用相同论文和相同模型；
- 评价者使用固定 rubric；
- “遗漏”必须有操作性定义。

### 机制假设

阅读卡强制分别记录任务、设置、结果和局限，因此能减少把局部结论写成普遍结论的情况。

### 外部输入

- 论文原文；
- 阅读卡格式；
- AI 生成摘要；
- 人工标注 rubric；
- 与论文阅读和主张核验相关的原始研究。

### 证据地图

- 现有流程错误样例；
- 阅读卡生成记录；
- 普通摘要与阅读卡流程的盲评结果；
- 评价者分歧与边界。

### 研究判断

主要指标选择“限定条件遗漏率”；通用流畅度只作为辅助观察，因为项目关注准确性而非语言质量。

### 原型验证

- 选择一小组论文；
- 固定模型、输入和温度等条件；
- 分别生成普通摘要与结构化阅读卡；
- 由不知道生成条件的评价者使用同一 rubric 标注；
- 保存所有结果，包括无差异和更差的样例。

### 回写表达

报告说明结构化阅读卡是否改善目标动作、在哪些论文类型中失败、人工成本是否增加，以及结论不能推广到哪些场景。

这个案例规模不大，却包含问题、机制、证据、判断、验证和边界，适合作为课程项目。课程不要求每个人做相同题目，但要求形成同样清楚的连接。

## 七、第 1 课项目起点

### 1. 最小目录

第 1 课只需建立轻量项目。这个目录不在课程仓库里，由你在自己的项目工作区中创建，填空模板见[早期研究脚手架](../../course/starter-template.md)；初始化命令（`git init` + 基线提交，diff 步骤的前提）见 [opencode-setup.md](../../course/opencode-setup.md) §六：

```text
project/
├── AGENTS.md
├── problem-definition.md
├── artifact-tracking.md
├── ai-usage-log.md
├── agent-permissions.md
└── notes/
```

各文件作用：

- `AGENTS.md`：项目目标、工作规则和 Agent 边界（模板"最小文件结构"提供最小模板）；
- `problem-definition.md`：问题、范围、非例和可证伪命题（模板 §3 问题定义初版）；
- `artifact-tracking.md`：关键工件状态及其来源、依据和后续用途（模板 §4 轻量工件追踪表）；
- `ai-usage-log.md`：AI 参与、Context、输出用途和人工核验（模板 §6 AI 使用记录）；
- `agent-permissions.md`：只读、可写、可执行、需确认和禁止范围（模板 §8 Agent 权限矩阵）；
- `notes/`：尚未进入正式工件的检索式、反馈和临时想法。

### 2. 当前只需要做到什么

第一讲结束时不需要搭建复杂实验工程，只需要：

1. 写出一个初步研究问题；
2. 写出至少一个当前不确定性；
3. 链路草图只标当前不确定位置（填一两行"主要不确定性"即可，多数行留空是正常的）；
4. 完成一次最小可审计交互；
5. 写下第一条 AI 使用记录。

第 1-6 课主要完善问题、外部输入、证据和伦理边界；第 7-8 课形成机制假设、研究判断和方案反馈；第 9 课明确 baseline 与实验规格后，再迁移到完整项目模板。

## 八、课堂练习

本课当堂的最低闭环是：围绕一个当前不确定性，完成“只读建议 → 人工判断 → 有限写回 → 检查 diff / log”，并在链路草图中标出它的位置。练习 1–4 是按需使用的课堂诊断或课后练习库，不要求每位学生在当堂全部完成；练习 5 只填当前不确定位置。

## 练习 1：主题、问题还是主张

判断以下表述属于主题、研究问题还是待验证主张，并说明缺失信息。

1. 大模型幻觉。
2. 检索增强生成能否减少医学问答中的事实错误？
3. 使用更多文献一定能提高综述质量。
4. 在固定来源集合和相同模型条件下，逐条引用核验是否降低主张—来源错配率？

参考判断：

- 1 是主题；
- 2 接近研究问题，但仍需明确场景、指标和比较条件；
- 3 是过强的待验证主张，需要定义“更多”和“质量”并考虑反例；
- 4 是相对可操作的研究问题。

## 练习 2：寻找非例

为自己的研究兴趣写出：

- 一个包含范围；
- 一个明确不包含范围；
- 一个容易混淆但实际上不属于本问题的非例。

如果无法写出非例，通常说明问题仍然过宽。

## 练习 3：区分线索与证据

假设 AI 告诉你：“某论文证明结构化提示能够消除引用幻觉。”

写出核验步骤：

1. 论文是否真实存在？
2. AI 给出的标题、作者和链接是否一致？
3. 原文研究的任务和设置是什么？
4. 原文说的是“降低”还是“消除”？
5. 结果来自什么指标和对照？
6. 结论适用于当前项目吗？

在完成这些步骤前，这句话只能是线索。

## 练习 4：改写越权任务

原任务：

> 扫描我电脑上的所有论文、数据和聊天记录，自动找出最适合的研究题目并建立项目。

## 九、术语表

| 术语 | 本课程中的含义 |
| --- | --- |
| Agent | 能够基于任务、上下文和工具执行多步动作并观察结果的系统 |
| Agent Workflow | 围绕明确科研动作设计的任务、状态、工具、权限、循环、评价和人工审核组合 |
| Artifact / 工件 | 可审查的研究产出，如问题定义、证据地图、判断记录、实验规格和评价报告 |
| Baseline | 用于解释改进是否成立的基准方法、流程或设置 |
| Context | 当前任务明确提供给 Agent 的材料和状态 |
| Evidence / 证据 | 可核验且能够支持、反驳或限制某项主张的材料或结果 |
| Evals | 对模型或工作流进行可重复评价的方法、数据、指标或 rubric |
| Gate / 研究门 | 项目进入下一阶段前的质量检查点 |
| Human-in-the-loop | 在关键判断、权限变化或外部动作上保留人工审核 |
| MCP | Model Context Protocol，用于连接模型与外部工具或数据源的协议 |
| Memory | 跨步骤保存的状态；本课程优先使用可审计项目工件和日志 |
| Skill | 将一类任务说明、资源和执行方法封装为可复用能力的一种形式 |
| Stable | 经充分检查的稳定工件状态；不表示引用资格，关键结论沿用课程独立证据要求 |
| Traceability / 可追溯性 | 从结论回到证据、实验、判断和来源的能力 |
