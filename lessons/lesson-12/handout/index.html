    第十二讲｜Agent/Skill 背后的逻辑与个人工作流设计¶

    导读¶

    第 10 课把一个编码或调试动作写成带验收标准的任务契约，并约束 Agent 的写入、执行与人工审核。第 11 课把可重复的科研动作改写为受限循环：固定指标、预算、停止条件、回退机制，并保留失败结果。两课都在回答同一个问题——当 AI 从"回答一次问题"变成"连续执行多步研究动作"时，研究者怎样继续对过程负责。

    本课把视角从"用一次 Agent"提升到"看懂一个 Agent/Skill 是怎样被设计出来的"。现成的 Agent、Skill、MCP 服务或工作流模板并不是黑箱魔法：它们都隐含着任务契约、Context、Memory / 状态、工具与权限、执行循环、工件与追踪、Evals 与人工审核、失败恢复八项设计决定。能否看懂这些决定，决定了你能否判断一个现成工作流是否适合自己的科研动作，以及能否把自己的科研动作封装成可审计的个人工作流。

    本课的核心不是"安装某个 Skill"，而是：

    1. 从现成 Agent/Skill 中抽取可迁移的八要素设计逻辑；
    2. 判断一个科研动作适合用确定性脚本、固定工作流、单 Agent 还是更复杂系统；
    3. 为自己的真实科研动作设计并最小实现一个可审计的个人 Agent Workflow，为第 13 课验证门评价和第 16 课论证门披露做准备。

    现成 Skill 可以作为参考实现，但课程不把"调用某个 Skill"当作学习目标。评分看你是否能说清八要素并接受评价，不看使用了多少工具。

    学习目标¶

    完成本讲后，你应该能够：

    1. 用八要素框架拆解一个现成 Agent/Skill，指出其隐含的任务契约、Context、Memory / 状态、工具与权限、执行循环、工件与追踪、Evals 与人工审核、失败恢复设计；
    2. 说明何时应使用确定性脚本、固定工作流（prompt chaining / routing / parallelization 等）、单 Agent 或更复杂系统，并给出取舍理由；
    3. 围绕自己当前科研动作，写出个人 Agent Workflow 的输入、输出、成功标准、不适用范围、权限边界、停止条件、人工审核点和失败恢复预案；
    4. 为该工作流设计一次可重复评价，包括 baseline、指标或 rubric、对照或等价依据；
    5. 在 OpenCode 或等价环境中完成可运行或可演示的最小原型，并保留运行记录与至少一次失败或局限；
    6. 把上述产物组织成可提交给第 13 课验证门的材料包前置状态。

    一、为什么从"使用 Agent"提升到"看懂 Agent"¶

    1. 一个常见误区：把调用当成理解¶

    学生很容易把"我装了某个 Skill""我用某个 Agent 跑通了一次"当作已经掌握 Agent 工作流。问题在于：现成 Agent 的任务边界、Context 选择、工具权限、循环停止条件和失败处理都是别人替你决定的。这些决定未必与你的科研动作匹配。

    一个为你导师组写综述的 Agent，可能默认允许联网检索；一个用于代码实验的 Agent，可能默认允许执行任意测试。直接挪用，等于把研究动作的边界让渡给一个你未审计的配置。

    2. 八要素是从第一课贯穿到本课的共同语言¶

    第 1 课 §四给出了 Agent Workflow 的八个组成部分。本课用它做"拆解工具"和"设计工具"的统一框架：

    组成部分 拆解现成 Agent 时问 设计个人工作流时问
    任务契约 它声称完成什么？输入、输出、成功标准和不适用范围是什么？ 我的科研动作要它完成什么？哪些不在范围内？
    Context 它能读哪些材料、工件和状态？ 我应给 Agent 哪些文件、数据、上一轮结果？
    Memory / 状态 哪些信息跨步骤保留，保存在哪里？ 状态如何写回可审计工件，而不是只在会话里？
    工具与权限 它能读、写、执行和联网到什么范围？ 我的最小权限是什么？哪些动作必须确认？
    执行循环 它如何计划、行动、观察、评价、停止？ 循环在哪一步可以停？预算和停止条件是什么？
    工件与追踪 输入、日志、输出和上游决定如何关联？ 一次运行留下哪些可复核工件？
    Evals 与人工审核 与什么 baseline 比、用什么指标或 rubric？哪些判断和外部动作必须人确认？ 我的工作流前后对比怎么设？哪些步骤决不能让 Agent 自行决定？
    失败恢复 超时、无效输出、工具失败或越权时怎么办？ 失败如何记录、回退和修订？

    八要素不是清单，是设计决定。每一项都需要你给出取舍理由和适用边界，而不是默认填满。

    二、八要素深度分析¶

    下面逐项展开。每项给出"拆解现成 Agent 时的观察点"和"设计个人工作流时的决策点"，并指出常见失败模式。

    2.1 任务契约¶

    任务契约回答"这个工作流到底在做什么"。一条可审计的任务契约至少包含：输入、输出、成功标准、不适用范围。

    拆解观察点：现成 Skill 的 README 或 SKILL.md 是否写明不适用范围？如果只写"擅长 X"而不写"不适合 Y"，使用者容易在边界外误用。

    设计决策点：把一个模糊科研意图收敛为可审计契约。例如：

    模糊意图：帮我把相关论文整理一下。

    任务契约：输入为按证据角色标注的论文清单（≤30 篇，每篇带 DOI 和 PDF 路径）；输出为一张证据地图 Markdown 表，包含"支持/反驳/冲突/空白"四列和原文位置；成功标准为每条主张可定位到原文页码且无 AI 自行补充的未标注文献；不适用范围为不在清单内的论文、非中英文文献、需要专业实验复现的论断。

    常见失败模式：契约只写目标不写非例；成功标准是"质量好"而非可测量；把"研究问题"和"任务输出"混淆。

    2.2 Context¶

    Context 是当前任务明确提供给 Agent 的材料和状态，不是"Agent 想看什么就看什么"。

    拆解观察点：现成 Agent 默认读取哪些文件、目录、URL？是否会把整个仓库或个人目录作为 Context？是否区分了"可读"与"应读"？

    设计决策点：遵循最小 Context 原则。只把完成当前任务所需的最小材料放进 Context；其余即使可读也不主动提供。Context 选择本身就是一种研究判断，应记录为什么纳入、为什么排除。

    常见失败模式：把整个 ~/Downloads 或整篇未公开论文塞进 Context，导致越权与许可风险；Context 过大导致模型注意力分散、引用错位；Context 选择未被记录，事后无法复现。

    2.3 Memory / 状态¶

    Memory 指跨步骤保留的信息。本课程优先使用可审计的项目工件（如 evidence-map.md、experiment-log.md、ai-usage-log.md）和结构化日志，而不是不透明会话记忆。

    拆解观察点：现成 Agent 把状态保存在哪里——会话内、外部数据库、还是可审查的文件？状态更新是否能被人工复核？

    设计决策点：选择可追溯的 Memory 形态。一次运行的关键中间结果应写回项目工件，使得"关掉会话后仍能复原当时状态"。会话内记忆可作为缓存，但不能作为唯一来源。

    常见失败模式：依赖会话历史作为唯一 Memory，重启即丢失；状态被 Agent 静默修改而无可审查 diff；Memory 与工件不一致，事后无法判断哪份是当时真实状态。

    2.4 工具与权限¶

    工具与权限决定 Agent 能读、写、执行和联网到什么范围。

    拆解观察点：现成 Agent 暴露了哪些工具？MCP server 授予了哪些权限？是否有沙箱、是否需要确认、是否允许 shell 执行？工具列表本身是否可审计？一个有用的对照案例是极简 harness Pi Coding Agent（pi.dev，钉死版本见 reading-list.md 第 12 课）：它默认只暴露 read/write/edit/bash 四个工具，刻意不内置权限弹窗，把风险控制外置给 Git、容器或使用者的扩展——用它对照 OpenCode 的显性权限配置，可以看清"权限内置"与"权限外置"是两种不同的设计决定，而不是功能多寡的差异。该案例只作分析对象，不进学生安装清单。

    设计决策点：遵循最小权限原则。按只读 / 可写 / 可执行 / 需确认 / 禁止五档划分。关键判断（如修改实验规格、删除失败记录、联网发送未公开数据、修改评价代码）必须保留人工确认。

    常见失败模式：为方便一次性开放全盘读写；允许 Agent 自行扩大权限；把"能执行 shell"默认当作"能执行任意 shell"；评价代码与执行代码未隔离，Agent 可改评价以"通过"。

    2.5 执行循环¶

    执行循环回答 Agent 如何计划、行动、观察、评价和停止。不是所有任务都需要自主循环。

    拆解观察点：现成 Agent 是固定工作流（按预定步骤走）、还是自主循环（自己决定下一步）、还是人在每步确认？它的停止条件是什么——任务完成、预算耗尽、还是人喊停？同一谱系上可以看到不同取舍：pi 把循环压到最小、把计划与子 Agent 移出核心；构建在 pi 之上的 Prime Agent 则把子 Agent 调用做成持久 REPL 中的程序化调用，并给自主模式配置预算与质量门（官方自述"通过门只证明该门所验证的内容"）。两者都只作分析对象（钉死版本与预印本标注见 reading-list.md 第 11/12 课），不外推为能力结论。

    设计决策点：先判断你的科研动作需要哪一类。Anthropic 在 Building Effective Agents 中区分了 prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer 和 autonomous agent 等模式。它们的可控性和适用场景不同：

    模式 适用 风险
    固定链（prompt chaining） 步骤清楚、每步可验收 步骤错误时全链失败
    路由（routing） 输入分类后走不同分支 分类错误级联
    并行（parallelization） 独立子任务可同时跑 合并阶段冲突
    编排者-工人（orchestrator-workers） 子任务动态分配 编排者误判
    评估-优化（evaluator-optimizer） 有明确评价器可迭代 评价器漂移
    自主 Agent 步骤不可预定、需观察后决策 难停止、难审计

    上述模式来自工程经验，不是经典理论。引用时应标注来源为 Anthropic 工程博客，而非学术论文。

    常见失败模式：把自主循环当作默认"高级"形态，而忽略固定工作流的可审计性优势；停止条件是"模型觉得做完了"，没有预算或人工闸门。

    2.6 工件与追踪¶

    工件与追踪要求输入、日志、输出和上游决定可关联。一次运行至少留下：任务契约、Context 清单、工具调用记录、中间结果、最终输出、diff、人工审核记录。

    拆解观察点：现成 Agent 是否生成可审查的 trace？trace 是否绑定到具体工件版本？能否从一条结论反向追到当时 Context、prompt 和工具结果？

    设计决策点：把工作流输出写成可追溯工件。每条 AI 生成的主张在进入项目前必须能回到原文、数据或实验 ID。课程要求 AI 使用记录包含工具/模型、用途、Context、输出用途和人工核验方式（见第 1 课与第 2 课）。

    常见失败模式：只保留最终输出不留中间步骤；trace 与工件分离，无法对应；Agent 自述"我修改了 X"以自述代替实际 diff 检查。

    2.7 Evals 与人工审核¶

    Evals 回答"和什么比、用什么指标或 rubric"；人工审核点回答"哪些判断和外部动作必须人确认"。两者都是对 Agent 输出的外部校准——前者看是否改善目标动作，后者守住不可让渡的人工判断。

    拆解观察点：现成 Agent 是否带评价？它的评价是自评还是外部评价？评价代码是否可被 Agent 修改？baseline 是什么？现成 Agent 在哪些位置要求人确认？越权动作是否被记录？

    设计决策点：为个人工作流设计一次可重复评价。至少包含 baseline（不用工作流时同一动作的结果）、指标或 rubric、对照或等价依据。关键结论的 stable 状态原则上需要两项相互独立证据（见第 1 课证据要求）。第 11 课强调：评价协议在工作流运行期间不可被篡改，失败结果不可被选择性删除。同时明确列出必须人工确认的步骤（如修改实验规格、删除工件、联网发送数据、修改评价代码、外部写入）。

    常见失败模式：只有"能跑"没有对照；Agent 既执行又自评；只保留成功结果；指标在迭代中被悄悄放宽；人工审核点未写在契约里，事后无法判断哪一步该有人。

    2.8 失败恢复¶

    失败恢复回答"超时、无效输出、工具失败或越权时怎么办"。

    拆解观察点：失败时现成 Agent 如何处理——重试、跳过、停止、还是静默继续？

    设计决策点：失败处理遵循第 1 课"记录→收窄→重试→核验"，不静默重跑到成功。每一次失败都是工作流评价材料，进入第 13 课失败复盘。

    常见失败模式：把"Agent 自己处理了"当作成功；失败被删除或重写；越权动作未被记录。

    三、何时不用 Agent：确定性脚本、工作流与 Agent 的取舍¶

    不是所有科研动作都需要 Agent。一个重要判断是：步骤是否可预先确定。

    • 确定性脚本：步骤清楚、输入输出明确、不需要模型判断。例如批量下载已知名单的 PDF、按固定 schema 生成统计表。用普通 Python 脚本即可，引入 Agent 反而增加不可控性。
    • 固定工作流：步骤可预定但每步需要模型能力。例如"读取论文→抽取主张→核验原文→写回阅读卡"是固定链。每步可单独验收，整体可审计。
    • 单 Agent：步骤不可预定，需要观察中间结果再决定下一步，但仍可设停止条件和人工闸门。例如调试一个未知错误，需要边读代码边假设边验证。
    • 更复杂系统：多 Agent 协作或长 horizon 任务。本课程不要求学生构建多 Agent 系统，但要求能说明何时它确实必要、何时是过度工程。

    第 11 课 AutoResearch 是一种受限循环：固定指标、固定预算、固定保留/丢弃规则，本质更接近 evaluator-optimizer 模式而非完全自主 Agent。理解这一点有助于判断自己的动作是否需要自主性。

    四、个人 Agent Workflow 设计¶

    4.1 从科研动作出发¶

    个人 Agent Workflow 必须服务一个你真实会做的科研动作，而不是"为了交作业造一个 Agent"。动作来源可以是：

    • 首选第 10–11 课已经建立的受限执行与失败恢复骨架；本课在原任务上增加 Context、Memory、工件追踪、Evals 与人工审核；
    • 如个人项目不是阅读卡任务，选择自己项目中一个已在第 10–11 课执行过的真实重复动作；
    • 只在缺少前置工件时才使用课程虚构阅读卡备用案例，不在本课新开另一个项目。

    工作流的评分不取决于使用了多少工具，而取决于它是否真实改善该科研动作并接受评价。第 13 课验证门要求"工作流针对一个明确科研动作，写清输入、输出、成功标准和不适用范围"。

    4.3 可审计要求¶

    工作流必须可审计，意思是：

    1. 一次运行能留下可复核 trace（任务契约、Context 清单、工具调用、中间结果、diff、人工审核记录）；
    2. 关键 AI 生成主张能回到原文、数据或实验 ID；
    3. 评价代码与执行代码隔离，Agent 不能修改评价以"通过"；
    4. 失败结果和越权动作被保留，不被静默删除；
    5. 工作流说明写入项目 agent-workflow.md（字段模板见 project-template.md §6），权限边界、运行记录、失败记录进入对应工件，第 13 课验证门可统一检查。

    4.4 最小实现¶

    本课不要求完整工程系统。可接受的最小实现包括：

    • 一份按 4.2 模板填好的工作流说明；
    • 一个可运行或可演示的原型（可以是 OpenCode 任务契约 + 工具调用、一个带 prompt 和脚本的固定链、或一个可演示的 evaluator-optimizer 小循环）；
    • 至少一次运行记录（含至少一次失败或局限）；
    • 一份评价计划（baseline、指标、对照）。

    第 13 课会要求"至少完成一次可重复评价"。本课先把评价计划写清，运行和评价可以在课后到第 13 课之间推进，不要求本课正式提交。

    五、贯穿案例：把同一阅读卡任务升级为工作流¶

    本案例不重开新项目。它直接承接第 10 课的受限生成任务和第 11 课的执行/失败恢复骨架。

    动作与任务契约¶

    • 动作：为同一批 20 篇公开计算机论文分别生成结构化阅读卡和自由摘要，保留可配对的输出、配置与日志。
    • 输入：冻结的 20 篇论文版本、两个已审核 prompt、相同模型/解码参数/最大输出长度、三个运行种子。
    • 输出：20 篇 × 2 条件 × 3 次 = 120 份输出，以及每份输出对应的配置、日志和状态。
    • 成功标准：每份输出都能追到论文、条件、种子和运行 ID；任何失败都留痕；工作流不改动评价协议。
    • 不适用范围：未公开论文、需要专业图表解析但原型未支持的文档、不允许进入当前模型 Context 的材料。

    Context、Memory 与权限¶

    • Context 只读冻结论文、两个 prompt、运行配置和任务契约；不提供人工基准标注、最终评分和同伴反馈。
    • Memory 只写入结构化的队列状态、原始输出和失败日志；不依赖会话记忆作为唯一状态。
    • 可写：新运行目录和状态日志；需确认：任何配置或 prompt 改动；禁止：修改人工基准、覆盖历史输出、删除失败日志。

    执行循环与工件¶

    • 模式：固定链与确定性队列，而不是自主 Agent；读取一个队列项→执行冻结条件→保存原始输出与日志→检查运行状态→进入下一项。
    • 预算：最多 120 份输出及事先写明的时间/token 上限；不因中间结果好看或难看而改变。
    • 停止：队列完成、预算触顶或出现配置/数据/评价协议漂移；回退后保留已有运行。
    • 工件：agent-workflow.md、队列配置、experiments/<run-id>/中的原始输出与日志、failure-log.md、ai-usage-log.md。

    Evals、人工审核与失败恢复¶

    • baseline 为同一论文的自由摘要条件；对照为结构化阅读卡条件。
    • 主指标为相对人工建立并复核的限定条件基准，摘要遗漏的限定条件数 / 该论文应保留的限定条件数；不得简化成“缺失字段数/5”。
    • 假设固定为 H1=字段约束使限定条件更易保留和核验，A1=任务转移，A2=标注提示效应，A3=文档结构效应。
    • 人工审核点：队列启动前、协议性停止时、失败恢复后、盲评与结果解释时。结果只能进入“支持/反驳/仍不能判断”，未显著不等于机制不成立。
    • 失败恢复：记录失败运行、拒绝越权改动、回退到稳定配置；普通技术失败进入修复和复盘，不冒充实验结果。

    六、与第 11 课、第 13 课的连接¶

    • 承接第 11 课：第 11 课的受限循环是本课工作流的执行循环部分。本课在其基础上增加 Context、Memory、工件追踪、Evals、人工审核和失败恢复的完整设计，把"一个能跑的循环"升级为"一个可审计可评价的工作流"。
    • 为第 13 课铺垫：第 13 课验证门要求工作流"有可运行或可演示原型""至少完成一次可重复评价""至少保留一次失败或局限分析"。本课产出工作流说明、原型和评价计划；课后到第 13 课之间完成运行和评价，第 13 课统一检查。

    七、课堂练习¶

    练习 1：拆解一个现成 Skill¶

    选择一个现成 Agent/Skill/MCP 服务（可从课程案例池或自己常用工具中选）。用八要素框架写出它的：任务契约、Context、Memory / 状态、工具与权限、执行循环、工件与追踪、Evals 与人工审核、失败恢复。指出至少两处隐含设计决定及其风险。

    练习 2：判断是否需要 Agent¶

    判断以下动作分别适合确定性脚本、固定工作流、单 Agent 还是更复杂系统，并说明理由：

    1. 把 100 篇已知 DOI 的论文 PDF 下载到固定目录。
    2. 为每篇论文生成结构化阅读卡并核验原文。
    3. 调试一个未知原因的训练失败。
    4. 自动探索一组超参组合并保留所有结果。

    练习 3：写个人工作流契约¶

    围绕第 10–11 课已执行的同一科研动作，按 §4.2 模板填一份工作流说明。完成任务契约、Context、工具与权限、执行循环、Evals 计划和人工审核点，并运行或演示一个最小路径，保留一条 trace。无法执行时，使用预置输入/输出/失败日志完成等价演示。

    练习 4：找出越权与失败¶

    假设阅读卡工作流提议读取人工限定条件基准，以便“针对遗漏优化输出”。指出它越过了哪些 Context、权限与评价隔离边界，写出停止—记录—收窄—重试—核验的具体动作。

    课堂、课后与验证门的边界¶

    • 课堂最低产出：在第 10–11 课同一任务上完成八要素工作流说明的最小字段；选择确定性脚本、固定链或 Agent 中的一种并说明理由；运行或演示最小路径；保留一条 trace 和一条失败恢复位置。
    • 课后补全：把原型工件、权限、状态和 Evals 计划写入 agent-workflow.md，并在第 13 课前准备一次可用于评价的运行结果。
    • 验证门完整条件：以 course/assignments.md Checkpoint 3 为准。本课不要求当场完成全部评价和提交自查。

    八、术语表¶

    术语 本课程中的含义
    Agent 能基于任务、上下文和工具执行多步动作并观察结果的系统
    Agent Workflow 围绕明确科研动作设计的任务、状态、工具、权限、循环、评价和人工审核组合
    Skill 将一类任务说明、资源和执行方法封装为可复用能力的一种形式
    MCP Model Context Protocol，连接模型与外部工具或数据源的协议
    Context 当前任务明确提供给 Agent 的材料和状态
    Memory 跨步骤保存的状态；本课程优先使用可审计工件和日志
    工件 / Artifact 可审查的研究产出，如证据地图、阅读卡、实验日志、diff、AI 使用记录
    任务契约 写明输入、输出、成功标准和不适用范围的可审计任务说明
    执行循环 Agent 如何计划、行动、观察、评价和停止
    工作流模式 prompt chaining / routing / parallelization / orchestrator-workers / evaluator-optimizer / autonomous agent
    Evals 对模型或工作流进行可重复评价的方法、数据、指标或 rubric
    Baseline 用于解释改进是否成立的基准方法、流程或设置
    人工审核点 / Human-in-the-loop 在关键判断、权限变化或外部动作上保留人工确认
    失败恢复 超时、无效输出、工具失败或越权时的记录、收窄、重试与核验流程
    Traceability / 可追溯性 从结论回到证据、实验、判断和来源的能力
