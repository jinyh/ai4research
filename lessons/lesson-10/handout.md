# 第十讲｜AI 辅助编码、调试与受限 Agent 执行

## 导读

第 9 课你已经把实验规格草图补全为可复现的判断门材料——baseline 公平、七字段完整、复现说明齐到种子、研究判断成案、同伴反馈已处理。判断门通过之后，项目进入阶段七"原型验证"。本课不是把 Agent 装上就让 它跑，而是回答一个更严格的问题：

> 当 Agent 修改代码、运行测试、归因错误时，研究者在哪里审核、用什么权限边界、留什么记录，才能让"Agent 帮忙"不等于"Agent 替代判断"或"Agent 污染实验"？

本课对应八阶段研究链路的阶段七"原型验证"中的受限 Agent 执行环节。它承接第 9 课实验规格中已标注的"哪些步骤拟用 Agent、哪些步骤必须人工"——那一列标注是本课任务契约的直接输入。本课也是模块四（第 10-13 课）的起点：第 11 课把受限的"一次执行"扩展为"自动化循环"，第 12 课把多次执行封装为可复用工作流，第 13 课评价工作流是否真的改善了研究动作。受限是循环和封装的前提——没有边界的一次执行不能被安全地重复，更不能被自动化。

完成本课后，你将产出一份任务契约、一段代码 diff、一份验证记录和一份失败记录。本课不正式提交，产出回写个人项目，作为第 13 课验证门材料的过程证据。

## 学习目标

完成本讲后，你应该能够：

1. 把一个模糊编码或调试请求改写为带验收标准的任务契约（Context / Permission / Non-goal / 人工审核点 / 失败恢复五字段）；
2. 为 Agent 设置分层权限：只读 / 可写 / 可执行 / 需确认 / 禁止，并说明为什么这样分层；
3. 对 Agent 产生的代码进行人工核验：diff 审查、测试先行、不把"模型建议这样做"当作研究判断的充分理由；
4. 区分修复根因、绕过失败和污染实验三种处理方式，并说明它们对结论可追溯性的不同影响；
5. 承接第 9 课实验规格，标出"哪些步骤拟用 Agent、哪些步骤必须人工"，并为本课选定的受限任务写出完整任务契约；
6. 记录失败与越权：当 Agent 修改无关文件、跳过测试或要求越权时，按失败记录而非静默重跑到成功；
7. 说明本课产出如何成为第 11 课自动化循环与第 13 课验证门评价的输入。

## 一、受限 Agent 执行在研究链路中的位置

八阶段研究链路中，阶段七"原型验证"在第 9 课只是起始——判断门要求一个可执行 baseline 或最小验证原型，不要求完整自动化。本课在判断门已过的基础上展开受限 Agent 执行：研究者把实验规格中已标注为"拟用 Agent"的步骤交给 Agent，但每一次执行都有任务契约、权限边界、人工审核点和失败记录。

| 输入（来自第 9 课与项目当前版本） | 本课处理 | 输出（向第 11-13 课） |
| --- | --- | --- |
| 实验规格中"哪些步骤拟用 Agent、哪些步骤必须人工"标注 | 把"拟用 Agent"步骤改写为任务契约五字段 | 一份可执行受限任务契约 |
| baseline 代码、实验配置与可运行测试 | Agent 在受限权限下修改目标文件、运行指定检查 | 代码 diff + 测试与失败日志 |
| 第 1-2 课 Agent 权限矩阵与伦理检查 | 落到本课具体任务：哪些文件只读、哪些可写、哪些命令可执行 | 权限分层记录 |
| 研究判断记录与可证伪命题 | 人工审核点决定 Agent 的修改是否进入项目 | 人工核验记录 |

> 与第 1 课的连接：第 1 课 §2.7 已要求"如果使用 Agent 或自动化循环，需要明确允许访问哪些文件、允许写入和执行什么、哪些动作必须人工确认、是否允许修改评价代码、失败日志是否保留、工作流何时停止"——本课把这一要求落到一次受限执行的完整链路上。

本课产出的是原型迭代的一轮记录，不是完整自动化系统。自动化循环在第 11 课展开，工作流封装在第 12 课展开，评价在第 13 课展开。

## 二、从模糊 prompt 到任务契约

### 1. 模糊 prompt 的问题

研究者最常见的请求形式是模糊 prompt：

> 帮我把 baseline 跑通，看看结果怎么样，有问题就改一下。

这种请求把"跑通""结果怎么样""有问题""改一下"四件事都交给 Agent 自行解释。Agent 可能：

- 修改与目标无关的代码以"让结果看起来更好"；
- 跳过失败的测试或注释掉断言；
- 修改评价协议而不是修改方法；
- 把单次运行的差异写成方法效应；
- 越过原定权限访问其他目录或联网。

模糊 prompt 的核心问题不是"可能出错"，而是"出错后无法追溯"——研究者不知道 Agent 做了什么、为什么做、依据什么标准，因此无法判断结果是否仍属于当前实验。

### 2. 任务契约五字段

本课要求把每一个交给 Agent 的编码或调试任务写成任务契约，至少包含五字段：

| 字段 | 内容 | 贯穿案例样例 |
| --- | --- | --- |
| Context | Agent 能看到哪些文件、配置、上游判断；本次任务在实验规格中对应哪一步 | 阅读卡摘要生成函数 `src/generate.py` 的 `generate_summary()`；实验规格 §步骤之 3"分别生成"；H1 主假设；不暴露标注者身份与最终 rubric 评分 |
| Permission | 只读 / 可写 / 可执行 / 需确认 / 禁止五层，列出具体路径与命令 | 只读：`experiment-spec.md`、`evidence-map.md`；可写：`src/generate.py`；可执行：`pytest tests/test_generate.py`；需确认：任何对 `configs/` 的修改；禁止：修改 `experiments/` 已有结果、修改 rubric、访问 `notes/` 同伴反馈 |
| Non-goal | 明确不做什么——防止 Agent 把任务膨胀 | 不优化生成速度；不替换模型；不修改 prompt 模板；不重跑历史实验；不写新测试 |
| 人工审核点 | 哪些动作必须由研究者确认才能继续 | diff 写回前人工审查；测试失败时停并等待研究者；任何对评价协议的改动须人工确认 |
| 失败恢复 | 超时、无效输出、工具失败、越权时怎么办 | 超时 60 秒 → 终止并记录；输出无法解析 → 保留原始输出与错误日志，不自动重试到成功；越权请求 → 拒绝、记录、报告研究者 |

任务契约不是 prompt 模板，是可被独立检查者复核的工件。它写在项目里（例如 `agent-tasks/<task-id>.md`），与代码 diff、运行日志和人工核验记录一起留存。

### 3. 模糊 prompt 与任务契约的对照

| 维度 | 模糊 prompt | 任务契约 |
| --- | --- | --- |
| 范围 | "把 baseline 跑通" | "修改 `generate_summary()`，使其在阅读卡路径强制调用字段约束，自由摘要路径保持不变" |
| 权限 | 未声明 | 五层显式列出 |
| 验收 | "结果怎么样" | 测试通过 + diff 只含授权范围 + 未修改评价协议 |
| 失败处理 | "有问题就改一下" | 超时终止、越权拒绝、不重试到成功 |
| 可追溯 | 无法复盘 | 契约 + diff + 日志 + 人工核验一一对应 |

> 来源参考：Russell, S., & Norvig, P. *Artificial Intelligence: A Modern Approach*, 4th ed., Pearson, 2020, Chapter 2 "Intelligent Agents"。用途：用经典 Agent 概念（agents and environments、rationality、environment properties、agent structure）理解 Agent 的任务、观察、行动与环境的边界，再分析 LLM coding agent。见 [reading-list.md](../../course/reading-list.md) 第 10 课。

### 4. ReAct 循环与错误传播

LLM coding agent 常采用 reasoning—action—observation 循环：模型先推理下一步、调用工具、观察结果、再推理。错误可能在任一环节传播——推理错误导致错误行动，行动错误产生错误观察，错误观察又强化错误推理。

> 来源参考：Yao, S. et al. "ReAct: Synergizing Reasoning and Acting in Language Models." *ICLR 2023*. [会议页面](https://iclr.cc/virtual/2023/poster/11003)。用途：分析 reasoning—action—observation 循环及其错误传播，理解为什么 Agent 输出必须被核验而不是被信任。

任务契约的存在不是为了消除错误传播，而是让错误传播可被观察——Agent 推理了什么、行动了什么、观察了什么，都有日志可查；任一环节出错，研究者可以定位到具体步骤，而不是面对一个"结果变了但不知道为什么"的项目。

## 三、权限分层与人工审核点

### 1. 最小权限原则的回归

第 1 课 §四·3 已建立最小权限原则：只读、可写、可执行、需确认、禁止。本课把它从"项目级权限矩阵"落到"任务级权限契约"。

| 层级 | 任务契约中的含义 | 贯穿案例样例 |
| --- | --- | --- |
| 只读 | Agent 可读取以理解 Context，但不得修改 | `experiment-spec.md`、`evidence-map.md`、`hypothesis-and-judgment.md` |
| 可写 | Agent 可修改的具体文件 | `src/generate.py` |
| 可执行 | Agent 可运行的明确命令 | `pytest tests/test_generate.py`、`python src/run_baseline.py --config configs/exp01.yaml` |
| 需确认 | 动作在 Agent 完成前必须由研究者审核 | 任何对 `configs/` 的修改、对 `rubric` 的修改、对 `experiments/` 已有结果的覆盖 |
| 禁止 | 无论任务如何表述都不允许 | 修改评价协议、删除失败日志、访问 `notes/` 同伴反馈、联网调用外部 API 上传项目数据 |

权限不是"开放到方便为止"，而是"开放到任务契约所需为止"。任务变小时权限随之收紧；任务结束后权限回收，下一次任务重新授权。

### 2. 人工审核点的位置

人工审核点不是"Agent 跑完后再看一眼"。它是任务执行中必须停下来等研究者确认的具体节点：

- **diff 写回前**：Agent 生成修改建议后，研究者在写回前审查 diff——只允许授权范围的修改进入项目；
- **测试失败时**：Agent 不得自行"修复"失败的测试以让测试通过；停，记录失败日志，等研究者判断是测试错误、实现错误还是评价协议问题；
- **评价协议改动时**：任何对 rubric、指标计算、数据划分的改动必须由研究者确认——这是"Agent 不污染实验"的底线；
- **越权请求时**：Agent 提出超出权限的请求时，研究者拒绝、记录、决定是否修改任务契约。

> 来源参考：Amershi, S. et al. "Guidelines for Human-AI Interaction." *CHI 2019*. DOI: [10.1145/3290605.3300233](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)。选读人工纠错、控制、反馈和失败处理相关准则。用途：设计人工审核点和可恢复交互，而不是假设 Agent 始终正确。见 [reading-list.md](../../course/reading-list.md) 第 10 课。

### 3. 为什么要预先写停止与确认

最常见的隐性偏倚是"Agent 跑到结果好看为止"。如果不预先写明停止与确认节点，研究者会在结果有利时接受 Agent 的越权、在结果不利时让 Agent 继续改，最终把 Agent 的修改序列写成方法效应。这与第 9 课 §三·2 停止条件的逻辑一致——预先承诺停下来，不是因为结果已经够好，而是因为"跑到结果好看为止"本身构成偏倚。

### 4. 失败恢复

失败恢复不是"重跑到成功"。一个完整的失败恢复段至少回答：

- 超时怎么办（终止并记录，不自动延长）；
- 输出无法解析怎么办（保留原始输出与错误日志，研究者判断是否修改任务契约）；
- 工具调用失败怎么办（记录失败工具与失败原因，不切换到未授权的替代工具）；
- 越权请求怎么办（拒绝、记录、报告研究者，不"变通执行"）；
- 测试失败怎么办（停，记录，等研究者判断根因，不"修测试让它通过"）。

失败日志与成功结果同等重要。删除失败日志等同于伪造实验记录（沿用 [assessment.md](../../course/assessment.md) 学术规范红线）。

## 四、Agent 产生的代码必须人工核验

### 1. Agent 输出是候选，不是事实

第 1 课 §一·2 已确定：AI 可以生成候选、执行重复步骤或帮助发现问题，但它无法自动获得对研究背景、学科规范、数据来源和潜在后果的完整责任。Agent 产生的代码同理——它是候选实现，不是已验证实现。研究者必须核验：

- **diff 审查**：修改是否只在授权范围？是否引入未授权的依赖、联网调用或对评价协议的改动？
- **测试先行**：测试是否在修改前就存在？如果 Agent 新增测试，测试是否先于修改被研究者审查？测试是否覆盖了关键路径还是只覆盖了容易通过的路径？
- **不外包判断**：方法选择、baseline 公平性、指标定义、停止条件等研究判断不能由 Agent 决定——Agent 可以提供候选，但判断与取舍理由必须由研究者写出。

### 2. 修复根因、绕过失败与污染实验

当 Agent 遇到失败时，处理方式分为三类，对结论可追溯性的影响截然不同：

| 处理方式 | 含义 | 对可追溯性的影响 | 例子 |
| --- | --- | --- | --- |
| 修复根因 | 找到失败的机制原因，修改实现或配置使根因消除 | 保留失败日志 + 修改记录 + 根因分析，结论可追溯 | `generate_summary()` 在自由摘要路径误调用了字段约束逻辑 → 修改分支条件，失败日志保留 |
| 绕过失败 | 不找根因，让失败不再出现——注释断言、跳过测试、调整数据使失败消失 | 失败被隐藏，结论无法追溯，等同于伪造记录 | 测试 `test_field_constraint` 失败 → 注释掉这条断言让它通过 |
| 污染实验 | 通过修改评价协议、数据划分或 baseline 使结果看起来更好 | 方法效应与评价效应混淆，结论不成立 | baseline 遗漏率高于实验组 → 调整 baseline 的温度参数使它"看起来更公平" |

修复根因是唯一被接受的处理方式。绕过失败与污染实验都是学术规范红线（沿用 [assessment.md](../../course/assessment.md)）。任务契约的"禁止"层与"人工审核点"层正是为了在 Agent 执行中阻止后两种处理方式——Agent 不允许修改评价协议、不允许删除失败日志、不允许在测试失败时自行修复。

### 3. diff 审查清单

对 Agent 产生的每一次 diff，研究者至少检查：

1. diff 是否只包含任务契约"可写"层列出的文件？
2. 是否引入未授权的新依赖或外部调用？
3. 是否修改了"禁止"层的文件（评价协议、失败日志、实验结果、notes 同伴反馈）？
4. 新增测试是否先于修改被审查？测试是否覆盖关键路径？
5. 修改是否在"Non-goal"层声明不做的事情上？
6. Agent 的 commit message 或 diff 注释是否把模型推断误写成事实（例如"优化了方法"而不是"修改了分支条件"）？

任一项不通过，diff 不进入项目。研究者决定是修改任务契约重新执行，还是回到机制假设与实验规格修订判断。

### 4. SWE-bench 视角：任务构造与测试判定

> 来源参考：Jimenez, C. E. et al. *SWE-bench: Can Language Models Resolve Real-World GitHub Issues?* ICLR 2024. [项目页面](https://www.swebench.com/original.html)。用途：只分析任务构造、执行环境、测试判定与 benchmark 局限；不要求复刻完整系统。

SWE-bench 把"代码任务"构造为：一个真实 issue、一个可执行的代码仓库快照、一组判定通过的测试。它的关键设计是把"Agent 解决了问题"定义为"指定测试通过"，而不是"Agent 改了一段看起来合理的代码"。本课借用它的视角——Agent 的修改是否被接受，由预先指定的测试判定，不由 Agent 自己的叙述判定。但 SWE-bench 的测试集是真实开源项目的既有测试，课程项目往往没有同等质量的测试集，因此研究者必须额外人工核验，不能把"测试通过"等同于"修改正确"。

SWE-bench 的局限也是本课的局限：测试通过不等于方法正确、不等于未引入数据泄漏、不等于未污染评价协议。Agent 输出始终需要人工核验。

## 五、贯穿案例：把判断门实验规格的一步改写为受限 Agent 任务

承接第 9 课贯穿案例。第 9 课产出：朴素 baseline（自由摘要）vs 实验组（阅读卡摘要）的七字段实验规格 + 复现说明 + J2（baseline 选朴素而非强）+ 同伴反馈处理 + 失败预案。实验规格 §步骤之 3 是"分别生成"——自由摘要组与阅读卡组分别调用生成函数。

本课动作链：

**第一步：从实验规格中标出"拟用 Agent"与"必须人工"步骤**

| 步骤 | 拟用 Agent | 必须人工 |
| --- | --- | --- |
| 1 抽 20 篇 | 否（数据划分须研究者确认） | 是 |
| 2 随机分两组 | 否（种子须研究者记录） | 是 |
| 3 分别生成 | **是**——本课受限任务 | 否（生成函数实现可由 Agent 修改，但 prompt 模板须人工确认） |
| 4 盲评 | 否 | 是 |
| 5 计算遗漏率与 kappa | 否（度量协议须人工） | 是 |

**第二步：为"步骤 3 分别生成"写任务契约**

- Context：`src/generate.py` 的 `generate_summary()`；实验规格 §步骤之 3；H1 主假设；不暴露标注者身份与最终 rubric 评分；
- Permission：只读 `experiment-spec.md`、`evidence-map.md`；可写 `src/generate.py`；可执行 `pytest tests/test_generate.py`；需确认任何对 `configs/` 的修改；禁止修改 `experiments/` 已有结果、修改 rubric、访问 `notes/`；
- Non-goal：不优化生成速度；不替换模型；不修改 prompt 模板；不重跑历史实验；不写新测试；
- 人工审核点：diff 写回前审查；测试失败时停；评价协议改动须确认；
- 失败恢复：超时 60 秒终止；输出无法解析保留原始输出；越权拒绝记录。

**第三步：Agent 执行与人工核验**

Agent 修改 `generate_summary()`，使阅读卡路径强制调用字段约束、自由摘要路径保持不变。研究者审查 diff：修改只在 `src/generate.py`、未引入新依赖、未修改评价协议、未删除失败日志。运行 `pytest tests/test_generate.py`——通过。研究者额外人工核验：字段约束逻辑是否符合 H1？自由摘要路径是否真的未被影响？新增测试是否覆盖关键路径？

**第四步：记录失败（假设 Agent 越权）**

如果 Agent 在执行中请求修改 `configs/exp01.yaml` 以"让 baseline 更公平"——这越过了"需确认"层。研究者拒绝、记录"Agent 请求修改 configs/exp01.yaml，理由：使 baseline 温度与实验组一致；判断：当前温度已一致，Agent 推理基于错误观察；处理：拒绝，不修改任务契约，记录本次越权"。失败记录与成功 diff 一起留存。

**第五步：写入项目**

- 任务契约：`agent-tasks/task-01-generate-summary.md`；
- 代码 diff：`src/generate.py` 的 commit；
- 验证记录：`pytest` 输出 + 人工核验清单；
- 失败记录：`experiments/exp01/agent-traces/task-01-failure-log.md`（含越权请求与拒绝）；
- AI 使用记录：`ai-usage-log.md` 增加一条——工具/模型、用途、Context、输出用途、人工核验方式、问题。

课堂最低负荷固定为五步：（1）从实验规格选一个受限步骤；（2）写任务契约与权限边界；（3）核对一份真实执行或课前预置 diff；（4）记录一条验证证据和一条失败/越权；（5）开始一条 AI 使用记录。环境就绪时可执行 Agent 与测试；环境故障时使用本课的[受限 Agent 任务契约](./assets/agent-task-example/task-01.md)、预置 diff、真实测试输出与[越权失败记录](./assets/agent-task-example/failure-log.md)做纸面审查。两条路径的最小产出相同，均回写 `agent-tasks/` 与 `experiments/<experiment-id>/agent-traces/`。

## 六、常见错误

1. **模糊 prompt 直接交给 Agent**：没有任务契约，结果无法追溯。应改写为五字段契约。
2. **权限开放到方便为止**：可写层包含整个 `src/` 甚至整个项目。应只开放任务所需的具体文件。
3. **人工审核点缺失**：Agent 跑完才看一眼，越权已经发生。应在 diff 写回前、测试失败时、评价协议改动时停下来。
4. **Agent 输出被当作事实**：代码能跑就接受，未审查 diff、未检查未授权依赖。应执行 diff 审查清单。
5. **绕过失败**：测试失败时让 Agent"修测试"让它通过。应停，记录，等研究者判断根因。
6. **污染实验**：通过修改评价协议、数据划分或 baseline 使结果看起来更好。这是学术规范红线。
7. **删除失败日志**：越权请求或失败运行被静默删除。应保留所有失败日志与成功结果同等留存。
8. **重跑到成功**：失败后自动重试直到结果好看。应预先写明停止与确认节点，失败即停。
9. **把"测试通过"等同于"修改正确"**：SWE-bench 视角的局限同样适用于课程项目。应额外人工核验方法是否符合 H1、是否引入数据泄漏、是否污染评价协议。
10. **任务契约一次性写完不再改**：任务执行中发现权限过紧或过松时不修订契约，而是变通执行。应在发现问题时修改契约并记录理由。
11. **Agent 修改评价代码**：让 Agent 修改 `rubric`、指标计算或数据划分。应把评价代码列入"禁止"层。
12. **越权未记录**：Agent 越权请求被口头拒绝但未写入失败记录。应把越权请求、拒绝理由与处理一并记录。

## 七、课堂练习

### 练习 1：模糊 prompt 改写

把以下请求改写为任务契约五字段：

> 帮我看看 baseline 为什么结果不好，改一下让它能跑。

参考改写：明确 Context（哪个文件、哪个函数、哪一步）、Permission（只读哪些、可写哪个、可执行什么、需确认什么、禁止什么）、Non-goal（不做什么）、人工审核点（diff 审查、测试失败时停）、失败恢复（超时、越权、输出不可解析的处理）。

### 练习 2：权限分层

为你第 9 课实验规格中的一个"拟用 Agent"步骤，列出五层权限。检查：可写层是否只包含任务所需的具体文件？禁止层是否包含评价协议与失败日志？

### 练习 3：diff 审查

给定一段 diff（教师提供或贯穿案例的 `generate_summary()` 修改），按 diff 审查清单六项逐项检查。标注哪项通过、哪项不通过、不通过时如何处理。

### 练习 4：区分修复根因 / 绕过失败 / 污染实验

下面三种处理方式各属哪一类？对结论可追溯性的影响是什么？

1. 测试 `test_field_constraint` 失败，Agent 修改 `generate_summary()` 的分支条件使字段约束只在阅读卡路径调用，测试通过。
2. 测试 `test_field_constraint` 失败，Agent 注释掉这条断言，测试通过。
3. baseline 遗漏率高于实验组，Agent 调整 baseline 的温度参数使两组接近。

参考判断：1 修复根因；2 绕过失败；3 污染实验。

### 练习 5：写任务契约

为你第 9 课实验规格中的一个"拟用 Agent"步骤，写完整任务契约五字段。重点检查：Context 是否暴露了不应暴露的信息（如最终 rubric 评分）？Non-goal 是否防止了任务膨胀？失败恢复是否预先写明停止与确认？

### 练习 6：失败记录

假设你的 Agent 在执行中请求访问 `notes/` 目录中的同伴反馈。写出失败记录：失败表现、可能原因、是否涉及权限或任务契约缺陷、如何修改工作流、修改后结果。

### 练习 7：人工审核点定位

在你的实验流程中，标出至少四个人工审核点。检查：diff 写回前是否是审核点？测试失败时是否停？评价协议改动是否须确认？越权请求是否拒绝并记录？

### 练习 8：SWE-bench 视角

阅读 SWE-bench 的任务构造与测试判定方式（[项目页面](https://www.swebench.com/original.html)）。回答：SWE-bench 把"Agent 解决了问题"定义为什么？这个定义的局限是什么？课程项目没有同等质量的测试集时，研究者必须额外做什么？

## 八、术语表

| 术语 | 本课程中的含义 |
| --- | --- |
| 任务契约 | 把一个交给 Agent 的编码或调试任务写成带验收标准的工件，至少含 Context / Permission / Non-goal / 人工审核点 / 失败恢复五字段 |
| Context | 当前任务明确提供给 Agent 的材料和状态；不包括不应暴露的信息 |
| Permission | 任务级权限分层：只读 / 可写 / 可执行 / 需确认 / 禁止 |
| Non-goal | 任务明确不做什么，防止任务膨胀 |
| 人工审核点 | 任务执行中必须停下来等研究者确认的具体节点 |
| 失败恢复 | 超时、无效输出、工具失败、越权时的处理方式；不重跑到成功 |
| diff 审查 | 研究者在 Agent 修改写回前对 diff 进行的范围、依赖、评价协议、测试覆盖检查 |
| 测试先行 | 测试先于修改被研究者审查，且覆盖关键路径而非只覆盖容易通过的路径 |
| 修复根因 | 找到失败的机制原因并修改使根因消除；保留失败日志与根因分析 |
| 绕过失败 | 不找根因，让失败不再出现（注释断言、跳过测试、调整数据）；等同于伪造记录 |
| 污染实验 | 通过修改评价协议、数据划分或 baseline 使结果看起来更好；方法效应与评价效应混淆 |
| ReAct 循环 | LLM coding agent 常采用的 reasoning—action—observation 循环；错误可在任一环节传播 |
| SWE-bench 视角 | 把"Agent 解决了问题"定义为"指定测试通过"，而不是"代码看起来合理"；测试通过不等于修改正确 |
| 受限 Agent 执行 | 在任务契约、权限分层、人工审核点和失败记录约束下的一次 Agent 执行；是循环与封装的前提 |
