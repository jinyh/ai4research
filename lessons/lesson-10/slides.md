# 第 10 课逐页脚本｜AI 辅助编码、调试与受限 Agent 执行

## 一、使用说明

### 本课唯一主目标

> 学生把第 9 课实验规格中一个"拟用 Agent"步骤改写为受限 Agent 任务契约，亲手完成一次有任务契约、权限分层、人工审核点和失败记录的执行。

本课不追求在 90 分钟内完成完整自动化系统，也不要求 Agent 把 baseline 跑到最优。目标是让学生亲手完成一次"实验规格标注 → 任务契约五字段 → Agent 执行 → diff 审查与人工核验 → 失败与越权记录"的可复盘链路。本课产出是第 11 课自动化循环与第 13 课验证门评价的过程证据。

### 适用条件

- 21-40 人；
- 连续 90 分钟；
- 中文授课，英文仅保留论文名、工具名和必要术语；
- 旧版正式 PPT 已有三重检查记录；本轮修订后须依新母稿重建并重走检查，规则见 [ppt-quality-gates.md](../../course/ppt-quality-gates.md) 与 [ppt-design-criteria.md](../ppt-design-criteria.md)；
- OpenCode、Git 和模型后端尽量在课前确认；
- 学生优先使用自己第 9 课实验规格中已标注的"拟用 Agent"步骤；没有者沿用贯穿案例；
- 本课非正式提交门，产出回写个人项目。

## P03｜模糊 prompt 让错误无法追溯

### 屏显内容

```text
模糊 prompt 让错误无法追溯

“帮我把 baseline 跑通，看看结果怎么样，有问题就改一下。”
跑通
可能修改无关代码
结果怎么样
可能把单次运行写成方法效应
有问题
可能跳过失败测试
改一下
可能改评价协议而非方法
```

屏显来源页脚：来源：lesson-10/slides.md；课程工件与讲义见 speaker notes。

### 视觉结构

上方保留模糊请求原句；下方逐一对照四个模糊词与对应风险。

### 教师讲述备注

模糊 prompt 把范围、权限、验收、失败处理都交给 Agent 解释。核心问题是出错后无法追溯——研究者不知道 Agent 做了什么、为什么做、依据什么标准，因此无法判断结果是否仍属于当前实验。本课的起点是把模糊 prompt 改写为任务契约。

### 互动／操作

让学生说出自己最近一次给 Agent 的 prompt 属于模糊 prompt 的哪些特征。

### 建议时间

4 分钟。

### 来源与事实边界

讲义 §二·1。

## P05｜任务契约把请求改写为可追溯执行

### 屏显内容

| 含混请求 | 可执行的任务契约 |
| --- | --- |
| “帮我把代码修好” | 补 normalize_record 的缺失字段检查 |
| 没有修改范围 | 只改 after/generate.py |
| “结果能用就行” | 既定两项测试通过，人工检查 diff |

### 互动／操作

让学生用对照表检查自己刚才写的五字段，标注哪些维度仍模糊。

### 建议时间

## P07｜错误循环需要可见的失败恢复

### 屏显内容

```text
错误循环需要可见的失败恢复

Reasoning
→
推理可能错
Action
→
行动可能越权
Observation
→
观察可能误导
停止并记录
阻断错误传播
超时 / 无法解析 / 工具失败 / 越权 / 测试失败
删除失败日志属于伪造实验记录。
```

屏显来源页脚：来源：Yao et al., 2023（ReAct）；课程处理口径详见 speaker notes。

### 视觉结构

Reasoning、Action、Observation 与停止记录构成横向链路，下方列失败触发器与日志红线。

### 教师讲述备注

ReAct 循环说明 Agent 输出必须被核验：错误会在推理、行动、观察任一环节传播并自我强化。任务契约与日志让错误传播可被观察。失败恢复不重试到成功——失败日志与成功结果同等重要，删除失败日志等同于伪造实验记录（沿用 [assessment.md](../../course/assessment.md) 学术规范红线）。

### 互动／操作

让学生检查自己任务契约的失败恢复段是否覆盖超时、越权、测试失败三种情形。

### 建议时间

2 分钟。

### 来源与事实边界

屏显来源页脚：来源：Jimenez et al., 2024（SWE-bench）；课程评价边界详见 speaker notes。

### 视觉结构

真实 issue、仓库快照、候选 patch、指定 tests 与人工核验横向排列；底部标明测试判定边界。

### 教师讲述备注

SWE-bench 把"解决"定义为"测试通过"而非"代码看起来合理"，本课沿用这一判定。课程项目往往没有 SWE-bench 级别的测试集，因此研究者必须额外人工核验。测试通过不等于方法正确、不等于未引入数据泄漏、不等于未污染评价协议。SWE-bench 只分析任务构造与测试判定。

### 互动／操作
