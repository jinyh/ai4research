# 从研究问题到检索式

把公开研究问题转换为可复盘的学术文献发现、入口核验和候选表记录。遵循 `lessons/lesson-03/handout.md` 的课程口径：AI 可以参与生成词网、扩展引文、委派多源查询和整理候选；对外部文献主张仍需回到来源核验。若检索结果、模型输出、Agent trace 或生成内容本身是研究对象，可作为有来源、输入和边界记录的研究数据，不自动视为外部主张的证据。

## 先确认范围

- 只处理论文、预印本和正式学术出版物。
- 把代码仓库、数据集、规范、博客、issue 和机构网页列为“外部线索”，不套用本 skill 的论文核验状态，也不自动核验。
- 只把公开问题描述发送给公开 API。不要发送未发表材料、学生信息、`.local/` 内容或其他敏感文本。
- 不自动访问 Scopus、Web of Science、CNKI 等订阅源；可以记录用户手动提供的检索结果。
- 不写综述、综合报告或文献内容摘要；把完整多主张精读移交给第 4 课流程。

## 收集输入

优先使用用户给出的内容；缺项时给出显式假设，并把问题版本标为“待人工确认”。记录：

1. 公开研究问题或宽泛主题；
2. 对象与场景、干预或观察对象、比较条件、结果指标；不适用的字段写明理由；
3. 可选的拟用主张，例如“准备用某类研究支持什么判断”；
4. 可选的年份、语言、文献类型和研究类型边界；
5. 可用的学术索引、语义检索与 Agent 工具；记录账户权限、公开／订阅边界和工具实际支持的能力。OpenAlex、Crossref、Semantic Scholar、arXiv 等均为可选来源，不把任何单一数据库设为默认路线。

研究问题定稿权属于用户。把检索结果导致的问题或关键词变化记录为新版本，不覆盖旧版本。

## 执行流程

### 0. 选择检索路线并声明能力

先根据问题类型、已知线索和可用工具选择一条或多条路线，不因熟悉某个数据库而固定走同一入口：

| 路线 | 适用信号 | 需要留下的记录 |
| --- | --- | --- |
| 词法／字段检索 | 术语稳定，需要精确限定标题、摘要、年份、类型或布尔关系 | 实际字段、语法、筛选条件与命中记录 |
| 语义检索 | 同一概念有多种表述，或词面查询漏掉相关工作 | 工具与模型／索引版本（可得时）、输入问题、相似度或排序信息、人工相关性判断 |
| 引文网络扩展 | 已有可信种子文献，需要追踪其前向／后向连接 | 种子文献标识、扩展方向、轮次、候选来源及其处置 |
| Agent 多源检索 | 需要跨多个来源、并行子查询、迭代改词或根据结果委派下一步 | Agent／Skill 名称与版本、委派任务、实际查询和来源、每路状态、合并去重规则及人工抽查 |

路线可以组合或随结果切换。语义相似度、引用数量和 Agent 排名用于发现与排序，不直接代表相关性、证据强度或纳入决定。工具宣称支持的能力要以本次运行核实；不能运行或无法确认时，记录为未执行，不补写假想结果。订阅索引可由用户在其授权环境手动检索，Skill 不绕过访问控制。

### 1. 写问题初稿与词网

- 把宽泛主题改写成能驱动第一轮检索的问题初稿，不声称它已完成问题定义。
- 从问题中抽出核心概念，为每个概念列出同义词、上位词、下位词和相关术语。
- 将可能需要精确匹配的关键词与适合语义扩展的概念分别记录；记录词项来自正式文献、综述、领域词表、AI 建议或研究者判断。
- 词项可直接进入探索性查询；若要据此作外部事实陈述，仍需核验具体来源和原文主张。

### 2. 写检索式和筛选标准

- 为每个目标库写可执行的实际语法；不要只保存跨库概念模板。
- 在检索前写第一版纳入与排除标准：年份、文献类型、语言、研究类型、与问题或拟用主张的相关性。
- 每次改式都记录版本、修改内容、理由和时间。

### 3. 执行公开检索并保留原始记录

当所选路线与脚本能力匹配时，运行随 Skill 提供的公开元数据查询脚本。该脚本覆盖若干公开 API，不代表完整的语义检索或 Agent 生态；下面的 OpenAlex 命令只是可运行示例，不是默认推荐来源：

```bash
python3 .agents/skills/research-question-to-search/scripts/search_public_sources.py \
  --source openalex \
  --query "research question terms" \
  --limit 20 \
  --output-dir .work/research-question-to-search/run-001
```

支持 `crossref`、`openalex`、`arxiv`、`dblp` 和 `semantic-scholar`。用 Crossref 核验已知 DOI 时：

```bash
python3 .agents/skills/research-question-to-search/scripts/search_public_sources.py \
  --source crossref \
  --doi 10.1145/1273445.1273458 \
  --output-dir .work/research-question-to-search/keshav
```

`--query` 是便捷入口，各库映射不同：Crossref 用 `query.title`，OpenAlex 用 `search`，arXiv 默认用 `all:"…"`。需要布尔、字段、年份或类型过滤时，优先用 `--raw-query` 传入该库的原生表达式或 URL 参数，例如：

```bash
python3 .agents/skills/research-question-to-search/scripts/search_public_sources.py \
  --source arxiv \
  --raw-query '(all:"large language model" AND ti:"code review")' \
  --limit 50 \
  --output-dir .work/research-question-to-search/arxiv-001
```

脚本只保存请求元数据、原始响应和规范化结果，不替人决定状态、角色或纳入。每次执行使用新的空目录；脚本拒绝覆盖已有 trace。若不能运行脚本，可用等价公开 API，但仍须保存实际请求、检索日期、原始响应和规范化字段。

动态数据库会更新；“可复盘”指请求、时间、原始响应、规范化方式和筛选规则可追溯，不要求未来重跑得到完全相同的排序或命中数。

对语义检索或 Agent 多源路线，除各源原始记录外，保存问题／提示版本、每个子查询及来源、工具可见的排序或相似度、跨源去重方式、执行失败和人工抽样结果。若工具不提供分数或原始响应，明确记为 N/A 及原因。不得把 Agent 汇总表当作可重放的源记录。

### 4. 建立检索与筛选记录

每次执行先记录检索运行状态：`success` / `zero-hit` / `http-error` / `network-error` / `parse-error`。这是查询级状态，不是文献核验四态；尚未形成具体文献条目时，不要创建“探索线索 + pending”的伪候选。

每次执行至少记录；多路任务同时增加路线名、工具身份和轮次，使每个结果能回到其实际来源：

```text
数据库｜实际检索式或请求参数｜检索日期时间｜时间范围｜运行状态
数据库报告总数｜本次返回数｜题名初筛数｜摘要初筛数｜建议纳入数｜人工确认纳入数
纳入条件｜排除条件｜原始响应路径（不存在时 N/A + 理由）｜备注
路线｜工具／Agent 与版本（可得时）｜子查询或委派任务 ID｜扩展轮次｜合并去重方式
```

逐条分开记录“筛选建议”和“人工筛选决定”。人工确认前，前者可写建议，后者保持空白并显示工作流标记 `awaiting-human`；`awaiting-human` 不是第四种课程筛选决定。人工确认后，决定只能是纳入 / 排除 / 仅留审计。筛选决定不是核验状态。

### 5. 做入口核验

对拟纳入的文献完成两层入口核验：

1. **身份层**：题名、作者、年份、刊会或出版物、DOI/arXiv ID 等稳定标识是否在正式来源一致；
2. **拟用主张层**：先写准备用它支持什么，再回到至少一个原文位置，核对任务、设置、措辞强度和必要限定。

只完成身份层时保持 `pending`，注明“身份已核，拟用主张待核”。把多条主张、完整指标、对照、样本、贡献和局限列入“待精读移交项”。

### 6. 分开记录三个维度

不要互相替代：

| 维度 | 允许值 |
| --- | --- |
| 预期证据角色 | 主证据 / 补充证据 / 对比证据 / 探索线索 |
| 核验状态 | `pending` / `verified` / `verified-with-caveat` / `rejected` |
| 人工筛选决定 | 纳入 / 排除 / 仅留审计；确认前为空并另标 `awaiting-human` |

角色必须相对于一个明确问题或拟用主张判断。默认使用“探索线索”；即使文献已核验，也可能仍是探索线索。只有用户确认参照问题和理由后，才建议主证据、补充证据或对比证据。

### 7. 建立审计记录与候选表

来源审计记录保留所有文献条目和 `rejected`；查询级失败进入检索运行记录，不伪装成文献条目。候选文献表只放“人工决定纳入且状态不是 `rejected`”的学术文献；`pending` 只能放在线索区。人工确认前可输出“候选线索区”，不得冒充正式候选表。

候选表使用这十个字段，不增删或混并：

```text
| 编号 | 题名（核验后） | 作者 | 年份 | 稳定来源 | 对应问题/拟用主张 | 预期证据角色 | 纳入理由 | 核验状态 | caveat/允许主张 |
```

把个人项目输出写入 `notes/literature-search.md`，除非用户指定其他路径。不要直接写入 `reading-cards.md` 或证据地图；那是后续课程工件。

十字段表不重复加入筛选决定；必须用“编号”作为外键，连接同文件中的筛选记录。交付前检查每个候选编号都有对应的筛选建议和人工决定状态。

### 8. 检索质量自评

学术检索没有“相关文献总数”分母，不声称“检索全面”，只把下列可检查项写入 `literature-search.md`（与讲义 §六“检索质量自评”一致）：

- 完整性：
  - 在本次检索之外独立建立 5-10 篇 must-find 基准集（综述核心引文、奠基论文、问题来源文献），记录命中数；禁止从本次检索结果中挑选基准集；无法建立时显式登记“未建立基准集 + 理由”；
  - 对已纳入核心论文做后向滚雪球（核对参考文献）与前向滚雪球（核对引用它的新文献），记录池外相关文献及处置；连续两轮无新相关文献时记录“当前策略下趋于饱和”；
  - 对语义或 Agent 多源扩展，检查各路线是否覆盖预先列出的主要问题要素；记录独有候选、重复和未覆盖来源，不以汇总命中数代替覆盖诊断；
  - 维护“问题要素 ↔ 检索分支”覆盖矩阵，不留空格；零命中分支按“处理失败”条款记死路，不解释为“不存在这类文献”；记录每条分支的独有相关文献数与词网反馈轮次；
- 代表性：
  - 候选池按方法族或子主题分组后，每个主要分组至少 1 篇代表纳入；
  - 对比证据存在，或其缺席标为红旗；
  - 年份、来源库、作者与机构独立性、结论方向、语言边界逐项记录；
  - 随机抽 5-10 条排除记录复核理由；
  - 每条拟用主张至少对应 1 条 `verified` 或 `verified-with-caveat` 的主证据或对比证据，否则记为缺口。

自评只报告实际执行的检查与结果，不写“已检索全面”。可在连续两轮引文扩展无新增相关文献、主要问题要素均有检索路径、可用资源或时间预算已到上限时停止；须记录停止条件、未覆盖范围及可能影响。AI 生成的自评判断可作为分析输入，最终结论由人工依据记录作出。

## 使用四态

| 状态 | 使用条件 |
| --- | --- |
| `pending` | 身份层或拟用主张层未完成；清楚写出已核和待核项 |
| `verified` | 书目信息和至少一条拟用主张与原文一致 |
| `verified-with-caveat` | 上述两层一致，但存在范围、方法、版本或措辞限定；同时保留 caveat、原文位置和允许主张 |
| `rejected` | 正式来源积极确认文献身份错误、不存在，或拟用主张与原文不符；只留审计记录 |

不要因为 DOI 缺失、解析器失败、付费墙或单一身份源无结果而标 `rejected`；已有文献条目在入口核验未完成时保持 `pending`。如果失败发生在尚无文献条目的查询层，只记录检索运行状态。状态升级到 `verified` 或 `verified-with-caveat`、最终筛选决定和正式候选表写入都须人工确认。

## 处理失败

- 0 命中或命中明显偏离：保留死路，提出改词、放宽字段或更换库的建议；不要覆盖失败记录。
- API 限流或超时：记录查询级运行状态、HTTP 状态和请求；切换备用公开源，不静默重复同一请求，不创建文献级 `pending`。
- 原文不可访问：身份可继续核验，拟用主张保持 `pending`。
- 来源冲突：并列记录冲突源、日期和字段；交给人工判断，不以多数票自动解决。
- 断网：停止外部执行，输出已完成记录和待办；不编造命中数、身份或主张。

## 交付格式

按以下顺序交付：

1. 问题初稿与待人工确认假设；
2. 关键词网与每库实际检索式；
3. 检索/筛选记录及原始文件路径；
4. 来源审计记录，包括失败和 `rejected`；
5. 候选文献表十字段；
6. 检索质量自评记录：基准集清单与命中数、滚雪球轮次、分支覆盖矩阵、代表性检查结论与红旗项；
7. 待精读移交项；
8. AI 使用记录与所有待人工确认项。

用下面的确认块结束建议阶段，允许用户逐条确认或批量确认：

```text
待确认：问题版本；筛选标准版本；条目编号→纳入/排除/仅留审计；
条目编号→核验状态与预期角色。未经确认不写正式候选表。
```

报告动态结果的检索日期。不要自动 commit、push、导入 Zotero 或修改课程三件套。

## 最小验证

- 用 Crossref DOI 查询重放 `lessons/lesson-03/source-audit-demo.md` 的 Keshav 记录，核对题名、作者、年份、刊名和 DOI；
- 检查网络失败不会自动产生 `rejected`；
- 检查 `rejected` 不进入候选表；
- 检查角色与核验状态有值；人工筛选决定有值，或明确带 `awaiting-human` 且未进入正式候选表；
- 检查每次运行都有 `request.json`、`summary.json` 和 `results.jsonl`；有响应体时保存原始响应，无响应体时在 summary 中写 `raw_response: null`；
- 检查查询级失败没有被写成文献级 `pending`；
- 检查候选编号能关联到筛选建议与人工决定状态；
- 检查基准集命中记录存在，或显式登记“未建立基准集 + 理由”；
- 检查覆盖矩阵在问题要素与检索分支之间无空格；零命中分支按失败条款记录；
- 检查候选表含对比证据，或其缺席已标红旗；
- 检查自评记录未声称“检索全面”，只报告实际执行的检查与结果。
